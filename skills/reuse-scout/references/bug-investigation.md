# 故障调查路线

1. 只读定位用户给出的错误和相关代码，提取异常类型、公开包/API、实际锁定版本、平台/运行时、触发条件、已尝试方式。只读测试定义不等于运行复现。
2. 本地已有明确原因时说明证据与最小修复建议；无外部比较要求就收敛。
3. 外部确有必要时先看对应版本官方文档，用脱敏的通用错误、公开包名/版本/平台或必要 API/运行时词组合查 Issue/PR，再读修复与发布的直接证据。搜索摘要只作线索；正文不可读或详情预算已尽时保留未知。不从无关热门仓库开始。
4. 相同错误的不同平台、运行时、版本、构建工具和部署模式分别核对；相邻版本证据只能支撑适配推断。

不要压缩以下状态链：

| 事实 | 可用的直接证据 | 不能推导的事实 |
| --- | --- | --- |
| Issue 关闭 | Issue 状态及关闭原因 | 维护者确认根因或修复成功 |
| 维护者确认 | 可归属的维护者回复、明确范围 | 已经合并或发布 |
| PR 合并 | PR merged 状态、目标分支与提交 | 用户可直接升级获得修复 |
| 修复已发布 | 发布说明、标签/提交包含关系或发布包证据 | 当前使用版本含修复 |
| 当前版本含修复 | 实际版本与上述发布证据匹配，必要时核对分支/回移 | 本项目在所有环境已恢复 |

发布说明没提 PR 不能单独证明修复不在包里；证据不够应写“发布状态未确认”。不同维护分支和 backport 需要单独核对。

提出最小建议时，按证据讨论配置/用法修正、已发布版本、等待发布或有明确代价的临时绕过。合并但未发布的补丁只能作为研究候选，不默认建议安装 main、执行任意 commit 或复制无许可片段。

验证计划交代：命令、平台/依赖版本、最小输入、预期从哪个错误变成什么信号，以及可能写入的缓存/产物/锁文件。仅获得执行授权后由普通开发流程运行；不要把“应该通过”写成实际结果。

最终注明已确认链条与未知环节。没有工具、未登录、权限不足、网络故障、限流分别描述，不能伪造查询或维护者结论。
