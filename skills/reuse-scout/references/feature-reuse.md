# 功能复用路线

先从本地接口和调用方确定最小能力：输入/输出、语言与版本、平台、运行位置、部署限制、依赖政策。不要把一个具体功能扩成平台建设。

1. 查相关模块、依赖清单、现有适配器和测试。已安装依赖的公开 API 足够时，给出可定位复用点；若本地已解决且用户未要求外部比较，停止。
2. 只在相关生态寻找包或工具，先看官方元信息和文档。读取包元信息不是安装包；不要执行包管理器安装或项目脚本。
3. API 或适配仍不明确时，再读官方示例、相应公开仓库及必要 Issue。用户明确要比较仓库时可直接检查指定候选，仍先确认本地约束。
4. 先淘汰硬约束不符的方案，再深入预算允许的少量候选。一个 monorepo 内解决同一问题的同一套组件算同一方案；独立替代方案分别计数。

候选应回答：最小复用表面是什么（函数/API、配置、CLI 或组件），适用版本与许可是否明确，需要改哪一层接口，会增加多少依赖和维护负担。规模、Stars 和发布时间仅在当次核实时使用；不代替适配分析。

| 决策 | 条件与应交付的建议 |
| --- | --- |
| 直接采用 | 能力与约束匹配；指向现有 API 和接入点，不自动安装 |
| 薄层适配 | 核心能力可用，只需转换输入/输出或少量配置；说明边界 |
| 组合 | 少量组件覆盖不同必要部分，交代接口与总依赖成本 |
| 自研 | 需求很小、已有方案过重或硬约束不符；说明最小实现和证据限制 |
| 暂不决策 | 许可、版本或关键功能无法确认；给出能解除不确定性的最小下一步 |

提出验证计划时，写具体检查、输入和预期信号，如边界输入、错误处理、平台兼容性。研究阶段不运行它们。
报告先说为何适合当前项目；未选候选仅列影响决策的原因。若无法找到匹配，不把搜索范围外的方案也判定不存在。
